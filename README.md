# Стандарт документов: ADR и карточки требований

Канон для всех проектов flow-scale. Репозиторий подключается в каждый проект как git submodule в
`docs/standards/`; проект пишет документы по шаблонам отсюда и проверяет их скриптом отсюда.

## Два типа документов

| Тип | Отвечает на вопрос | Где лежит в проекте | Шаблон |
|---|---|---|---|
| ADR, architecture decision record | почему система устроена так, а не иначе | `docs/architecture/decisions/` в lead-magnit, `docs/decisions/` в call-analysis-service | [adr-template.md](adr-template.md) |
| REQ, карточка требования | что должно получиться для бизнеса и как проверить, что получилось | `docs/requirements/` | [requirement-template.md](requirement-template.md) |

Требование ссылается на ADR, которыми его реализуют. ADR ссылается на требования, ради которых
принят. Факты о текущем состоянии системы в оба типа не пишутся: они живут в area-доках
(`docs/integrations.md`, `docs/contracts/`, схемы), документы на них ссылаются.

Карточка требования описывает одно проверяемое изменение. Исходные ТЗ от маркетолога и заказчика
разбиваются на такие карточки: одна карточка на одно поведение, которое можно принять или отклонить
отдельно. Текст ТЗ целиком не копируется, в карточке остаются ссылка на раздел источника и, если
нужно, короткая цитата.

## Идентификаторы

- Формат: `<проект>/ADR-NNNN` и `<проект>/REQ-NNNN`. Проект называется полным именем репозитория:
  `lead-magnit/ADR-0003`, `call-analysis-service/REQ-0012`. Так ссылка из другого проекта читается
  однозначно.
- Номер четырёхзначный, сквозной внутри проекта и типа, по порядку. Номер не переиспользуется:
  если документ отозван, файл остаётся со статусом `Withdrawn` и одной строкой, почему.
- Имя файла: `NNNN-короткий-слаг.md`, слаг латиницей через дефис. Номер в имени файла, в `id` и в
  заголовке H1 один и тот же.

## Фронтматтер

Каждый документ начинается с блока YAML. Это машиночитаемая часть: по ней скрипт проверяет
документы и собирает индекс. Значения плоские: строка, дата, `null` или список в квадратных скобках.

Поля ADR:

| Поле | Значение |
|---|---|
| `id` | `<проект>/ADR-NNNN` |
| `status` | `Proposed`, `Accepted`, `Superseded`, `Deprecated`, `Rejected`, `Withdrawn` |
| `date` | дата создания документа, `YYYY-MM-DD` |
| `decided_by` | `owner`, если решение принял человек; `agent`, если это предложение агента |
| `decided_on` | дата решения человека или `null` |
| `supersedes` | список `id`, которые этот документ заменяет |
| `superseded_by` | `id` заменившего документа или `null` |
| `requirements` | список `id` требований, ради которых принято решение |

Поля REQ: те же, кроме `requirements`; вместо него `source` (строка: файл и раздел исходного ТЗ или
кто и когда попросил) и `decisions` (список `id` ADR, которыми требование реализуется).
Статусы REQ: `Draft`, `Approved`, `Implemented`, `Rejected`, `Superseded`, `Withdrawn`.

Правила, которые проверяет скрипт:

- `Accepted`, `Deprecated`, `Approved`, `Implemented` требуют `decided_by: owner` и дату в
  `decided_on`. Предложение агента остаётся `Proposed` или `Draft`, пока человек его не принял.
- `superseded_by` заполнен тогда и только тогда, когда статус `Superseded`. Ссылки `supersedes` и
  `superseded_by` двусторонние и ведут на существующие файлы.
- Ссылки на документы того же проекта должны существовать.

## Решение человека и предложение агента

Документ различает их явно, а не интонацией. `decided_by: owner` и `decided_on` ставятся только по
явному решению человека в разговоре или в задаче, с датой. В разделе «Статус» это решение называется
словами: «Решение заказчика 2026-11-02». Всё остальное агент оформляет как `Proposed` или `Draft` с
`decided_by: agent`. Переписывать предложение агента в принятое решение задним числом нельзя.

## Обязательные разделы

ADR, в этом порядке: `# NNNN. Название`, `## Статус`, `## Контекст`, `## Рассмотренные альтернативы`,
`## Принятое решение`, `## Последствия`, `## Открытые вопросы`.

REQ, в этом порядке: `# NNNN. Название`, `## Статус`, `## Источник`, `## Проблема`, `## Цель`,
`## Пользователи`, `## Границы`, `## Критерии приёмки`, `## Открытые вопросы`.

Раздел «Статус» начинается со слова статуса из фронтматтера, дальше одна-две строки: кто решил и
когда, что заменяет, где реализовано. «Открытые вопросы» обязателен и при отсутствии вопросов
содержит «Нет.» «Границы» делятся на «Входит» и «Не входит». Критерии приёмки нумеруются, каждый
проверяется наблюдением или тестом.

Необязательные разделы добавляются после обязательных, когда их требует содержание: «Изменения»,
«Диаграмма», «Связи», «Метрика», «Дополнение YYYY-MM-DD». Дополнение не переписывает принятое
решение, а записывает, что изменилось и когда.

## Замена документа

Заменяющий документ перечисляет заменённые в `supersedes`. У заменённого статус становится
`Superseded`, заполняется `superseded_by`, а первой строкой раздела «Статус» идёт баннер:
«Superseded. Заменён `<проект>/ADR-NNNN` от YYYY-MM-DD». Тело заменённого документа не правится и не
удаляется: оно история.

## Индекс

В каждом каталоге документов лежит `README.md` с таблицей между маркерами `docs-index:start` и
`docs-index:end`. Таблицу собирает скрипт, руками её не правят. Строка индекса: номер, название,
статус, кем заменён. Пересказ решения и история замен в индекс не попадают, они в самом документе.
Текст выше маркеров свободный.

## Проверка

```bash
node docs/standards/scripts/check-docs.mjs            # проверить документы и индексы
node docs/standards/scripts/check-docs.mjs --write    # пересобрать индексы
node docs/standards/scripts/check-docs.mjs --strict   # файлы без фронтматтера считаются ошибкой
node docs/standards/scripts/check-docs.mjs --dir docs/standards/examples/adr --no-index
```

Скрипт запускается из корня проекта. По умолчанию проверяются `docs/architecture/decisions/` и
`docs/requirements/`; проект с другими каталогами передаёт их через `--dir`. Файлы без фронтматтера
до миграции дают предупреждение, не ошибку, поэтому CI остаётся зелёным. После миграции проект
включает `--strict`. Проект ставит проверку в свою цепочку: `npm run check` в lead-magnit,
`make check` в call-analysis-service.

## Подключение в проект

```bash
git submodule add https://github.com/flow-scale/docs-standards.git docs/standards
git submodule update --init          # у разработчика после clone
```

В CI шаг checkout получает `submodules: true`, иначе каталог `docs/standards/` пуст и проверка не
запустится. Обновление канона в проекте: `git -C docs/standards pull` и коммит нового указателя
submodule. Симлинк на соседнюю папку не используется: он требует `core.symlinks=true` и режима
разработчика Windows, зависит от раскладки каталогов на диске и в CI указывает в пустоту.

## Закрытые источники

Папки вида `_private/` не считаются источником: они держат черновики вне git. Если в такой папке
лежит документ, на который ссылается ADR или требование, его переносят в репозиторий, в каталог вне
`.gitignore`, и ссылаются на него по относительному пути. Ссылки абсолютными путями на диск другого
человека в документы не пишутся.
